# Frameworks: Andrew Ng

21 frameworks, roughly most-used first. Built from the notes on all 16 sources: Machine Learning Yearning (S001, 2018), How to Build Your Career in AI (S002, 2022), the Lex Fridman interview (S003, 2020), and the CS229 lecture notes (S004 to S016). "Sources" counts distinct sources where the idea is used. Names are his where he named them; otherwise a short name is marked *(unnamed)*. How-to-score lines are scoring guidance for the council, drawn from his thresholds, not quotes. SVM, ICA, EM, and PCA algebra from the course notes is left out except where it changes a data decision.

## 1. Bias, variance, and optimal error *(unnamed split in S001)*
- **What it is:** A split of the error that tells you whether the next month is for the model or for the data. Training error stands in for bias. Dev error minus training error stands in for variance. Optimal error, the Bayes rate, is the unavoidable bias. Training error minus optimal error is the avoidable bias.
- **Parts:** Estimate optimal error first, from the best humans you can actually assemble. Then compare optimal, train, and dev. High avoidable bias: increase the model size. High variance: add training data. His numbers: optimal 14%, train 15%, dev 30% is avoidable bias of 1% and variance of 15%, so the work is variance. The same train and dev errors with optimal error near 0% need bias work too. Older (2012, S005): bias is the error left even with infinite data, variance is fitting accidents of a small sample, and a larger hypothesis class lowers bias while raising variance, so it needs more examples. Newer (2018, S001): with a well-designed regularization method you can usually grow the model without growing overfitting. Keep the 2012 warning when the family cannot represent the pattern at all, such as a line through curved data. The 2018 split is informal on purpose. S005 says there is no agreed formal definition for classification, so do not wait for one. S004 calls the pair the two ways a model fails to generalize. S006 shows underfitting against a curve that passes through every training point. S003 (2020): both scale and new algorithms matter, and which one matters depends on how close you are to human level or Bayes error. S002 (2022) names bias and variance as core concepts, ahead of any one model.
- **When to use:** The number is short of the target and the team is about to choose more data or a new model by taste.
- **How to score:** Guidance. No optimal-error estimate: the choice is not ready. Avoidable bias near 1% and variance near 15%: score more data high. Train error already far above the target: score more data low and score a bigger model high. A regularized net with a large avoidable bias: score a larger model high.
- **Quote:** "If you have high avoidable bias, increase the size of your model" (S001)
- **Sources:** 6 (S001, S002, S003, S004, S005, S006)

## 2. When more data helps *(learning curves)*
- **What it is:** More data is a tool for variance. It does not rescue a model whose training error is already worse than the target. A learning curve checks that before anyone spends months collecting.
- **Parts:** Plot dev error against training set size, and plot training error on the same axes. Mark the error you want. If the dev curve has flattened, or training error already sits above the desired error, more data by itself will not get you there. If training is expensive, plot uneven sizes, such as 1,000, 2,000, 4,000, 6,000, and 10,000. Average a few resampled subsets only when the small-size curves are too noisy to read. His case: you want 5% error, training error is 15%, dev error is 16%. Adding data will not help much. In theory, enough data can drive a pure variance gap toward zero (S001). S003 (2020): run the test before a six-month collection project. Engineers still burn half a year because they heard that more data is valuable. For many problems still far from human level, bigger datasets with neural nets are enough without a new algorithm, and people who can debug this are easily 10x, maybe 100x faster. S005 (2012): more data shrinks variance and the gap between training error and error on new examples drawn the same way. It does not fix a model of the wrong kind. S006: with enough data, a locally weighted fit makes the feature choice less critical; with less data, features have to be chosen with care. S007: on a very large set that is not Gaussian, logistic regression almost always beats Gaussian discriminant analysis; with little data, the stronger model can win.
- **When to use:** Someone proposes a collection or labeling budget as the plan.
- **How to score:** Guidance. Desired error 5%, train 15%, dev 16%: score more data near zero. A falling dev curve with training error already under the target: score more data high. A flat dev curve: score more data low even if the story is scale.
- **Quote:** "Looking at the learning curve might therefore help you avoid spending months collecting twice as much training data, only to realize it does not help." (S001)
- **Sources:** 5 (S001, S003, S005, S006, S007)

## 3. Small data: features, and a smaller model *(unnamed)*
- **What it is:** When the training set is small, what you choose to measure beats which algorithm you shop for. When the number of columns crowds the number of rows, restrict the model instead of forcing a full fit.
- **Parts:** Around 20 examples, hand-built features move the result more than the choice of algorithm. Around a million examples, he favors a neural network (S001, 2018). On a small training set, feature selection is useful. Do not keep adding features because more sounds better (S006). If the feature count is very large and the training set is small, cut features before fitting or you overfit (S004). A wrapper search adds or drops one feature at a time by cross-validated error. It works, and it is expensive, on the order of n squared calls to the learner. A filter scores each feature alone and is only a heuristic. Choose how many features to keep by cross validation. Keep the course algebra thin and keep the decision: when the number of examples is not well above the dimension, a full covariance is a poor fit, so restrict the model (S011). Two columns that are the same quantity in two units are redundant. Remove that before modeling (S012). Fewer input dimensions mean a smaller hypothesis class and less overfitting (S012).
- **When to use:** A team with a few dozen or a few hundred labeled rows is debating algorithms, or the table is wider than the sample can support.
- **How to score:** Guidance. About 20 labeled examples: score a feature or labeling pass above an algorithm bake-off. About a million examples: score a larger neural net above more hand-built features. A wide, short table with no cut: score the plan low until someone restricts it.
- **Quote:** "the hand-engineering of features will have a bigger effect than the choice of algorithm." (S001)
- **Sources:** 5 (S001, S004, S006, S011, S012)

## 4. Dev and test sets that match the future *(unnamed checklist)*
- **What it is:** Dev and test sets exist to point the team at the changes that matter. They have to come from the distribution you expect in the future and want to do well on, and they have to share that one distribution.
- **Parts:** Do not take them as a random slice of whatever training data you happen to have. A cat detector split on website photos can ace its test set and fail on phone photos from users. Dev and test drawn from different markets make it hard to see what is working. Size the dev set so it can see the differences you care about. 100 examples cannot see a 0.1% change. 1,000 to 10,000 is common. Do not make the sets larger than you need. The test set only has to be big enough to trust the final number. On a new application, set an initial dev set, test set, and metric in under a week. That week does not apply to a mature product such as anti-spam. Those can justify months. "But this one week timeline does not apply to mature applications." (S001) Change the sets or the metric when they stop pointing the right way. Three reasons: the real distribution has moved, so get new data; you overfit the dev set, seen when dev is much better than test, so get a fresh dev set; the metric ranks the wrong system, so change the metric. A public benchmark whose dev and test disagree rewards luck more than skill (S001). Older (2012, S004): when data is abundant, hold out about 30%, somewhere from a quarter to a third, and train on the rest. When data is scarce, that price is too high. Use k-fold, typically 10 folds, or leave-one-out when data is really scarce. Newer (2018, S001): the old 70/30 train/test heuristic does not apply once data is plentiful. Dev and test can be far less than 30%. Use the 2018 sizing on large application data, and the 2012 k-fold rule when you truly have little data. S005: the guarantees assume train and test from the same distribution, and independent training draws. If that is false, the guarantees do not apply. S003 (2020): after deployment the world still moves, a tree cut down, a bird in the factory, a change in the lights, and a dramatic shift is still unsolved. Rebuilding the dev set is the move you do have.
- **When to use:** Setting up a project, inheriting a benchmark, or noticing that the offline number and the product disagree.
- **How to score:** Guidance. Dev or test drawn from training data while users will come from somewhere else: score low until the sets are rebuilt. Dev and test from different regions: score low. A metric that prefers a model the product cannot ship: change the metric. A new product with no dev set after a month of building: score low. A mature system that took time to get the set right: do not apply the one-week rule to it.
- **Quote:** "Choose dev and test sets to reflect data you expect to get in the future and want to do well on." (S001)
- **Sources:** 4 (S001, S003, S004, S005)

## 5. Model selection on data the model did not train on
- **What it is:** The tempting method is to train every candidate on all the data and keep the one with the smallest training error. Higher-order models always fit the training set better, so this always picks the most complex model. He rejects that method.
- **Parts:** Hold-out cross validation: split off a hold-out set, about 30% in the 2012 notes, train each candidate on the rest, and pick the lowest hold-out error. You may then retrain the winner on all the data. Skip that retrain if the algorithm is very sensitive to its starting point or to small changes in the data (S004). k-fold when data is scarce: k disjoint pieces, train on all but one, average the k errors. A typical k is 10. Then retrain the winner. Leave-one-out, k equal to the number of examples, when data is really scarce. The same procedure chooses a polynomial degree or chooses among an SVM, a neural net, and logistic regression (S004). A curve through every training point is not a good predictor of the next house (S005, S006). In product work the dev set is where you decide. The test set is off limits for decisions, including a rollback, and a periodic test reading is only for tracking (S001, 2018, newer than the course notes). He usually skips statistical significance tests for interim progress (S001).
- **When to use:** Comparing models, features, or hyperparameters, or when someone wants to check the test set before the choice is frozen.
- **How to score:** Guidance. A winner chosen by training error scores low. A winner chosen by peeking at the final test set scores low. A winner chosen on a hold-out or by k-fold, with one final test read after the choice is frozen, scores high. If data is scarce and about 30% was thrown out, score k-fold above a fat hold-out.
- **Quote:** "This algorithm does not work." (S004)
- **Sources:** 4 (S001, S004, S005, S006)

## 6. Error analysis: count about 100 mistakes *(the ceiling)*
- **What it is:** Before building an idea, look by hand at about 100 dev examples the system got wrong and count what share falls in each cause. That share is a ceiling on what fixing the cause can win.
- **Parts:** Use a spreadsheet. One column per category, plus a comments column. An example can tick more than one column. Add columns as patterns show up. Dogs at 5% of the errors means a 10% error can fall to 9.5% at best. Dogs at 50% of the errors can take 90% accuracy to 95%. Choose by share, by how much progress you expect, and by effort. There is no formula. At about a minute an image, the count is under two hours, set against a month of building. He has seen many engineers reluctant to do it (S001). How many errors to inspect: 10 is very small, about 20 is a rough sense, about 50 a good sense, about 100 a very good sense. People have gone to 500. Rarely go past 1,000. On a large dev set, split an Eyeball set from a Blackbox set. You look only at the Eyeball set. The Blackbox set is for automatic scoring, model choice, and tuning. His sizing: 5,000 dev examples at 20% error is about 1,000 errors. A random 10% of the dev set, 500 examples and about 100 errors, is the Eyeball set. The other 4,500 stay Blackbox. If the Eyeball number improves much faster than the Blackbox number, you have overfit the examples you stared at. Get fresh ones. Eyeball size is about 100 divided by the error rate, so a 5% error needs about 2,000 examples. A Blackbox set of 1,000 to 10,000 is often enough. If the dev set is small, use all of it as the Eyeball set. S002 (2022): exploratory analysis and error analysis are what drive data-centric progress, and machine learning engineers spend large amounts of time iteratively cleaning data. S003: the people who debug well are easily 10x, maybe 100x faster, because they run the test that says what is worth trying. Limits, from S001: the count is a guide, not a formula that names the top task. It works best when humans can do the task. The book is for people building applications, not for people whose goal is a paper.
- **When to use:** Any proposal to spend serious time on one error category, one feature, or one research idea.
- **How to score:** Guidance. No hand count: score the proposal low, however exciting it is. A category that is 5% of errors cannot justify a month. A category that is about half the errors can. Eyeball gains that the Blackbox set does not share: score the conclusion low until the count is repeated on fresh examples.
- **Quote:** "These two hours could save you a month of wasted effort." (S001)
- **Sources:** 3 (S001, S002, S003)

## 7. Idea, code, experiment *(build a basic system, then iterate)*
- **What it is:** Start with an idea, implement it, run an experiment that says how well it worked, and go round again. The speed of that loop is the speed of progress.
- **Parts:** Build a basic system in a few days, then let its errors choose the direction. Do not open by designing the perfect system. Even a system far from the best one you can build is worth reading (S001). A dev set and one metric make each lap fast. Hours of playing with the app will not show a 0.1% gain, and dozens of those gains add up. Even experienced researchers try many dozens of ideas before something is satisfactory. He had worked extensively on anti-spam and still could not pick, up front, among honeypot data, text features, and header features. S002 (2022): while building the model inside a product, build a working slice quickly and revise it, because a study rarely names the right model, the right data, or the right hyperparameters. He calls that slice an end-to-end system. That phrase is the loop, not the architectural choice in the end-to-end framework below. S003: ship the small feature and see if anyone uses it. A shared-login feature he was sure about had zero users, because people watch alone.
- **When to use:** The team is still in slides, or a founder who knows the domain is sure they already know which error to chase.
- **How to score:** Guidance. A basic system in a few days that produces errors you can count scores high. A month of design before any errors scores low. Domain expertise does not raise that score.
- **Quote:** "The faster you can go round this loop, the faster you will make progress." (S001)
- **Sources:** 3 (S001, S002, S003)

## 8. Ready, Aim, Fire versus Ready, Fire, Aim
- **What it is:** His 2022 name for when to study and when to build. Aim first when execution is expensive and a study can show whether the project is worth it. Fire first when a shot is cheap.
- **Parts:** Aim first if you would otherwise build an expensive customer-service chatbot before you know whether restaurants, airlines, or telcos are the right vertical. Fire first when you can try the thing, see if it works, and pivot after a little work. When shots are cheap, take many. For the model itself he leans Ready, Fire, Aim. Spend more time up front on costly investments and one-way doors. Do not spend a month deciding on a project that would take a week to build. Older habit, which he says he has left: when he was younger he executed the first idea that excited him (S002). Newer (2022, S002): brainstorm several solutions, then pick the mode from the cost of the shot. That the 2018 book is the fire-first manual for the model, and the 2020 interview is the aim-first manual for a company bet, is inferred from S001, S002, S003. The company bet in S003 is a count of customer calls, plus a check that the technology can be built, because a paper result is far from production.
- **When to use:** Choosing between a study and a build, or between one big bet and several small ones.
- **How to score:** Guidance. A cheap trial with a long study in front of it scores low. A costly or hard-to-undo bet with no study and no customer check scores low. A one-week project that has already consumed a month of meetings scores low.
- **Quote:** "Ready, Aim, Fire tends to be superior when the cost of execution is high and a study can shed light on how useful or valuable a project could be." (S002)
- **Sources:** 3 (S001, S002, S003)

## 9. Start small, then expand *(pilot first)*
- **What it is:** The first project should teach the organization and earn trust. A giant first project usually fails before it teaches anything.
- **Parts:** For a company's first machine learning effort, pick a small project with a real internal user. At Google Brain the first internal customer was the speech team, not web search and not ads. The second was Maps, reading house numbers in Street View. Only after those two wins did he talk to Ads (S003). The same shape applies to a person's first model. S002: class projects, then personal projects, then projects that create value, which bring compute, labeling budget, and head count, then rising scope. Wins make the next ask easier. S001 says the same thing about the system itself: examine a basic system even when it is far from the best you can build. He points to his AI Transformation Playbook for the longer company path (S003). That playbook is not in this corpus, so do not invent its steps.
- **When to use:** A company wants its first win to be the flagship workflow, or a founder wants the platform before any single use works.
- **How to score:** Guidance. A first project that needs a new team, a new data platform, and a flagship workflow scores low. A small project a real team already wants, shipped so the organization learns, scores high. Speech before ads is the pattern. It is not a rule that speech is the right domain.
- **Quote:** "I've seen a lot more companies fail by starting too big than by starting too small." (S003)
- **Sources:** 3 (S001, S002, S003)

## 10. Strong assumptions if you are sure, weak ones if you are not
- **What it is:** A model that assumes more about the shape of the data needs less data when the assumption is true, and it fails when the assumption is false. A model that assumes less is more robust and hungrier for data.
- **Parts:** Gaussian discriminant analysis assumes each class is roughly bell-shaped. When that is true it is more data efficient than logistic regression. Logistic regression assumes less and is much more robust when the shape is off. On a very large set that is not Gaussian, logistic regression almost always wins, which is why he says it is used more often (S007). Naive Bayes assumes the features are independent given the class. The assumption is extremely strong, and the classifier still works well on many problems. It is often a good first build because it is simple. Never let one unseen event drive a probability to zero. Smooth the counts. For text, his notes prefer the multinomial event model over the word-present model. S006: pick the family from the kind of target, a number, a yes or no, a count, or several classes, rather than by habit. The Gaussian-noise story is a justification for least squares, not a requirement. Newer application of the same trade (2018, S001): a large enough neural net can take extra data that shares one input-to-label mapping. A small or inflexible model cannot, and then training data has to match dev and test much more carefully. The practical order, a simple baseline before a heavy model, is inferred from S001, S006, S007.
- **When to use:** Choosing a model family under a data constraint, or deciding whether a crude baseline is worth a week.
- **How to score:** Guidance. You are confident the shape is real, and data is scarce: score the stronger model high. You are unsure of the shape: score the weaker model high. A very large non-Gaussian set: score logistic regression or a flexible net above Gaussian discriminant analysis. No simple baseline on the board: score the plan lower until one has been run.
- **Quote:** "Logistic regression makes weaker assumptions, and is significantly more robust to deviations from modeling assumptions." (S007)
- **Sources:** 3 (S001, S006, S007)

## 11. A portfolio of tools *(his phrase in S003)*
- **What it is:** The team should use the tool that fits the day, including tools that are not deep learning. Fashion is not a selection method.
- **Parts:** Some days a neural net, some days PCA, including a look at PCA residuals on a manufacturing problem (S003, 2020). Naive Bayes is often the right first classifier because it is easy to build (S007). S004: the held-out comparison is the same whether the candidates are polynomial degrees or an SVM, a neural net, and logistic regression. Older (2015, S008): the SVM notes call support vector machines among the best off-the-shelf supervised learners, and say many people believe they are the best. That ranking is older than the portfolio. Newer (2020, S003): the team should not use only deep learning. The 2018 companion, which is not a vote for a single family, still stands inside deep learning: a bigger network and more data remain a reliable way to improve (S001). Kernels, margins, and the SVM optimizer are course machinery. They do not change the decision beyond the wide-margin idea that a snug fit is fragile, and the soft-margin cost when one outlier can swing the boundary (S008).
- **When to use:** A team is standardizing on one fashionable model, or citing the 2015 ranking as a reason to skip a baseline.
- **How to score:** Guidance. One family on the board and no simple baseline: score low. A baseline plus the model the data shape justifies, chosen on held-out data: score high. An SVM-only plan justified by the 2015 ranking: score low under the 2020 rule, unless a fresh hold-out says otherwise.
- **Quote:** "some days we use a neural net, some days we use a PCA." (S003)
- **Sources:** 3 (S003, S004, S007)

## 12. Generated data: representative, or theater
- **What it is:** Synthetic examples can close a gap between training data and the real distribution. They are theater when the fake source is narrow, or when a person thinks they look real and the model can tell they do not.
- **Parts:** Adding car noise to quiet speech, or motion blur to sharp images, can work. The failure mode is a tiny source repeated: one hour of noise under 1,000 hours of speech, noise from 10 cars, or 100,000 images from 20 video-game car models. The model learns the quirks of the fake data, and people cannot see it. Check the synthetic set against the dev and test distribution. Do not leave a tell that lets the model split synthetic examples from real ones. His teams have sometimes needed weeks before the details were close enough to help, and the payoff was then a much larger training set (S001). There is no guarantee. Newer, and a different tool (2020, S003): self-supervised learning builds a labeling task from unlabeled data, such as predicting a rotation, a deleted word, or the order of nine patches, trains on it, and transfers the hidden representation. He calls that a way to generate unlimited labels, and he calls it a piece of the solution, not the whole thing. A free label is not evidence that the product distribution is covered. Measure the downstream task. That these are two different generation methods, with one shared test, is inferred from S001, S003.
- **When to use:** A demo, a synthetic-data vendor, a simulator, or a self-supervised pretrain is offered as the reason the model will work.
- **How to score:** Guidance. Synthetic data from a handful of sources, judged by eye: score it as theater. A synthesis pipeline that has been checked against the dev distribution: score it high, including one that took weeks to get right. Self-supervised pretraining scores high only if the downstream error moves. A realistic demo with no dev-set check scores low.
- **Quote:** "it is sometimes easier to create synthetic data that appears realistic to a person than it is to create data that appears realistic to a computer." (S001)
- **Sources:** 2 (S001, S003)

## 13. Training versus dev mismatch *(training-dev set)*
- **What it is:** When training data and dev data come from different distributions, one dev error mixes variance with mismatch. Carve a training-dev set from the training distribution so you can see which problem you have.
- **Parts:** Compare training error (bias), error on unseen data from the training distribution (variance), and dev error (mismatch, once variance is known). His case: 1% on train, 1.5% on unseen train-distribution data, 10% on dev. That is mismatch, not variance. Then find what differs, cars, noise, phone cameras, and get training data that matches the dev examples that fail. One split he uses: of 10,000 real user examples, put 5,000 into training and the rest into dev and test. S003 (2020) is the newer limit on this procedure: a dramatic gap between test and training distributions is still something the field handles badly. Domain adaptation and transfer learning exist, and he says we are not good at them. The 2018 steps still apply. The 2020 line means you do not treat a large shift as a solved trick. There is no guarantee the matching data exists (S001).
- **When to use:** The training corpus and the users' data come from different places, or a factory, camera, or channel has changed.
- **How to score:** Guidance. Distributions differ and there is no training-dev set: score the diagnosis low, because variance and mismatch are tangled. A gap that shows up between training-dev and dev: score a data-matching project high and an architecture project low. A dramatic shift whose only plan is the phrase transfer learning: score low.
- **Quote:** "Try to understand what properties of the data differ between the training and the dev set distributions." (S001)
- **Sources:** 2 (S001, S003)

## 14. Label noise triage
- **What it is:** Bad labels matter in proportion to the error you have left. They matter much sooner when the set is small.
- **Parts:** Add a Mislabeled column to the error spreadsheet. At 10% error, if bad labels cause 0.6% absolute error, which is 6% of the errors, fixing them is optional. At 2% error, the same 0.6% is 30% of the errors, and it is worth fixing, because it swamps the accuracy estimate. Apply the same fix to the test labels. Also look at examples the model got right, or the evaluation is biased. Teams often tolerate dirty dev and test labels at the start and change their minds as the system improves. Revisit the call (S001). Newer, and stricter for small sets (2020, S003): with a hundred examples, 10 wrong labels are 10% of the data. Inspectors disagree with each other and with themselves over a day, and the same person's calls can change between morning and afternoon. Write the labeling rules and clean the labels. Averaging disagreements is fine when you have a billion users. It is the wrong move on a few hundred industrial images. Outside consumer internet, the datasets are small.
- **When to use:** A labeling fight, a small inspection set, or a model that has improved enough that the remaining error might be the labels.
- **How to score:** Guidance. Bad labels are a small slice of a large error: do not stop the roadmap to clean them. They are a large share of the remaining error, or about 10% of a hundred-example set: cleaning outranks a new model. Cleaning dev and leaving test dirty: score low.
- **Quote:** "If you have only a hundred examples, these little labeling errors, if 10 of your hundred labels are wrong, that actually is 10% of your data set has a big impact." (S003)
- **Sources:** 2 (S001, S003)

## 15. From a test score to a deployment *(the gulf)*
- **What it is:** A model that scores well on a laptop has cleared the first step. Most of the system, and most of the ways it fails, are still ahead.
- **Parts:** Plan for the environment changing: lights, a tree cut down outside the window, a bird through the factory (S003). The machine learning model is maybe 5% of the code, or even less. Someone has to build the rest and make it reliable. Decide who acts when the system flags a defect, and redesign the tasks around the step you automated. Plan operations for a site that does not have 20 engineers on call. Teams underestimate these steps. S002 (2022): you cannot write a schedule that promises the date of the target accuracy, because you do not know it in advance. After the system hits the target, drift still needs more iteration. He also says the field does not yet have stable names for a lot of this operations work (S003). A vocabulary is not a method.
- **When to use:** A pitch ends at a test-set number, or a pilot is about to be called a product.
- **How to score:** Guidance. A plan that stops at test accuracy scores low. A plan that names the environment changes, the software around the model, the person who handles the output, and drift after launch scores high. A budget that is almost all model work, against his figure of about 5% of the code, scores low.
- **Quote:** "There's a huge gulf between something that works in a Jupyter notebook on your laptop versus something that runs in a production deployment setting" (S003)
- **Sources:** 2 (S002, S003)

## 16. One number, then satisficing, plus a business metric
- **What it is:** The team needs one number that can rank two models. Other goals become pass/fail bars. A product also needs a business number, because test accuracy is not the business.
- **Parts:** Precision and recall alone cannot rank two classifiers. In his example, 95% and 90% give an F1 of 92.4% (S001). For several goals, optimize one metric and set every other criterion as a satisficing bar. Maximize accuracy subject to a running time of at most 100 milliseconds. For a wake word, minimize false negatives subject to at most one false positive per 24 hours. If the metric ranks a system you would not ship above one you would, stop trusting it and change it. Newer (2022, S002): milestones include an ML metric such as accuracy and a business metric such as revenue or engagement. Not every business problem reduces to test-set accuracy. If you cannot set reasonable milestones, that is a sign you need to learn more, perhaps with a short proof of concept. The 2022 business metric sits beside the 2018 single ML number. You need both. On a mature product, teams sometimes chase 0.01% because it hits profit (S001). That is a reason to keep the number honest. It is not a place to start.
- **When to use:** Choosing among models, setting a launch bar, or judging a project that quotes only accuracy.
- **How to score:** Guidance. Two metrics and no way to rank: score low. One optimizing metric with explicit pass/fail bars: score high. A product plan with an accuracy target and no business milestone: score the business decision low, by the 2022 rule. A metric that prefers the model you would not ship: replace the metric.
- **Quote:** "Having a single-number evaluation metric speeds up your ability to make a decision when you are selecting among a large number of classifiers." (S001)
- **Sources:** 2 (S001, S002)

## 17. Human-level performance as the yardstick
- **What it is:** Compare to humans for three reasons. Labels are easier to get. Error analysis has a human intuition to lean on. The best human result is a stand-in for optimal error, and it gives the team a target.
- **Parts:** Define human level as the best you can get, not a typical person. He would use a team of doctors at 2% as the proxy, not a junior doctor at 10%, because optimal error cannot be worse than a result people already achieve. His medical imaging ladder runs 15%, 10%, 5%, and 2% for a debating team of doctors. Once the system is already good, use the best team. If humans beat the model on a subset, such as fast speech, work that subset. A reachable target speeds the team up. Progress is usually slower once machines pass humans, and faster while they are catching up (S001). S003 (2020): a few datasets may already be near Bayes error or past human level, and there is a ceiling you will not pass. Both data and algorithms matter more as you get close. Limit (S001): the yardstick is for tasks humans can do. If they cannot, much of the error analysis around it does not apply.
- **When to use:** Setting a target error, or deciding whether the remaining gap deserves a research program.
- **How to score:** Guidance. A target of perfect, or better than an unnamed person: score low. A target set to the best realistic human team, with avoidable error measured against it: score high. A roadmap of large gains after the model has already passed that team: score low.
- **Quote:** "I find that having a reasonable and achievable target error rate helps accelerate a team’s progress." (S001)
- **Sources:** 2 (S001, S003)

## 18. End-to-end versus a pipeline
- **What it is:** One model from raw input to final output is reasonable when you have a lot of labeled pairs for both ends. With little paired data, hand-built stages carry knowledge the data does not.
- **Parts:** More hand-engineered components let a speech system learn with less data (S001). Choose stages that are individually simple and for which labels are easy to get. A cat detector plus a breed classifier needs less data than one model that must find a Siamese cat in one shot. If every stage is near human level on the input it sees, and the whole system is far below a human who sees the whole scene, the pipeline is missing information and has to be redesigned. In his driving example the parts were human-level and the car was not, because the planner never saw lane markings. As of the 2018 draft he is skeptical of end-to-end driving, and he thinks the non-end-to-end approach is much more promising until the paired data exists. With little data, most of what the system knows has to come from human insight (S001). S003: after you automate a step, redesign the work around it. The practical driving failure he names is a car that does not brake for a truck across the road. Do not read the 2022 line about building an end-to-end system quickly as cancelling this. There it means a working product slice in the idea, code, experiment loop. inferred from S001, S002.
- **When to use:** Choosing an architecture when labeled pairs are scarce, or when every module looks good and the product does not.
- **How to score:** Guidance. End-to-end with scarce paired labels: score low. A pipeline of simpler functions with labels you can actually get: score high. Every part near human level and the product far from it: score a redesign above more tuning of the current stages. End-to-end driving, on the 2018 evidence: score low until the paired data exists.
- **Quote:** "When this type of data is not available, approach end-to-end learning with great caution." (S001)
- **Sources:** 2 (S001, S003)

## 19. Scope the project from the business problem *(five steps)*
- **What it is:** His 2022 sequence for deciding whether an AI project should exist. It starts from the business, not from a model.
- **Parts:** First, name a business problem, not an AI problem. Ask a domain expert for the top three things they wish worked better, and why those things are still broken. Second, brainstorm several solutions. Do not build the first one that excites you. Third, check feasibility, from published work, from what competitors did, and from a short proof of concept, and check value with the domain experts. Fourth, set milestones, both an ML metric and a business metric. If you cannot, learn more. Fifth, budget data, people, time, and support from other teams. If a step shows the direction is impossible, go back. Sometimes there is no good AI solution, and stopping is a fine outcome (S002). S003 runs the same gate on a startup: how many customer calls until there is validation, and can the technology actually be built. A mistake on a couple of key decisions, how you sell, how you market without buying expensive ads, and who the first engineering leader is, can decide the company. Keep asking whether the customer would give a thumbs up. A common startup failure is building something nobody wanted (S003).
- **When to use:** A new AI project, a pivot, or a pitch that opens with a model or a demo.
- **How to score:** Guidance. A pitch that starts from a model, with no domain expert's problem and no business milestone: score low. A pitch that names the problem, a feasibility check, an ML number, a business number, and the data and people: score high. Stopping because there is no good AI solution: score that as the process working.
- **Quote:** "Identify a business problem (not an AI problem)." (S002)
- **Sources:** 2 (S002, S003)

## 20. Use all the data only when one mapping fits *(consistency test)*
- **What it is:** Extra data from another source is not free performance. It helps when both sources share one input-to-label mapping and the model is flexible enough. It hurts when the same input should get different labels.
- **Parts:** Web cat photos and phone cat photos can share one mapping, and a large enough net can take both. Housing prices cannot. A house of a given size should not be pooled across New York City and Detroit if you only care about New York, and pooling them hurts. Data that teaches nothing about the target should be left out to save compute. When the extra source is much bigger, he uses a case of about 40 to 1, or very different, give it a lower weight tuned on the dev set, instead of building a giant net only to absorb it. Inside the 2018 book he describes an older practice: mixing sources was risky with earlier algorithms, and engineers warned against it. Newer, in that same book: the risk has greatly diminished for large flexible networks. The consistency test still applies. The down-weight still applies. This change is inside S001. There is no later source.
- **When to use:** Someone wants to pour in a second dataset, a public corpus, or a scraped pool.
- **How to score:** Guidance. The same input would get two labels: score pooling low, whatever the model. One shared mapping and a large flexible net: score pooling high. A dump on the order of 40 to 1 from a different source, at equal weight: score low until the weight is tuned on the dev set. Data kept only because it was on disk: score low.
- **Quote:** "If you only care about predicting New York City housing prices, putting the two datasets together will hurt your performance." (S001)
- **Sources:** 1 (S001)

## 21. Attribute the failure to a part before you staff it *(unnamed)*
- **What it is:** Two counts that stop a team from improving the wrong piece. One splits search from scoring. One splits a pipeline into stages.
- **Parts:** Optimization verification: the system picks the best-scoring output with an approximate search. Compare the score of the correct answer with the score of what the system actually output. If the correct answer scores higher, the search is at fault. If not, the scoring function is at fault. Count this on dev errors. If 95% of the errors are scoring and 5% are search, better search can remove at most about 5%. The same comparison works for a reward versus a reinforcement learning algorithm: compare the reward of the human trajectory with the reward of the machine trajectory. His helicopter autorotation case is that comparison (S001). Pipeline attribution: for each dev error, feed a perfect output into one stage, such as a hand-labeled box for the detector, and see whether the final answer becomes right. Attribute the error to the first stage whose fix makes the answer right. If 90 of 100 errors sit in the cat detector and 10 sit in the breed classifier, work on the detector.
- **When to use:** A team wants to fund a search project, a reward redesign, or one stage of a pipeline.
- **How to score:** Guidance. A plan to improve the model, with no attribution: score low. About 90% of errors in one stage: that stage gets the people. Search is about 5% of errors: a search project scores low. The correct answer already outscores the system's output: score search work high and scoring work low.
- **Quote:** "By attributing errors to specific parts of the pipeline, you can decide how to prioritize your work." (S001)
- **Sources:** 1 (S001)
